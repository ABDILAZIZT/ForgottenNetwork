# Shared-world HTTP API contract

Status: Phase 2 design baseline  
Base path: `/api/v1`  
Last updated: 2026-09-08

The TypeScript payload contracts live in `shared/src`. This document defines transport behavior. Phase 4 will implement these endpoints and add generated OpenAPI output from runtime validation schemas.

> Phase 4 implementation note: the current canvas engine uses the versioned full-chunk snapshot compatibility endpoints documented in `PHASE_4_IMPLEMENTATION.md`. The pixel-operation contract below remains the production target because it supports smaller atomic edits and safer conflict reconciliation.

## Conventions

- JSON request and response bodies use `camelCase`.
- Database columns use `snake_case` and are never returned directly.
- IDs are UUID strings generated by the client for idempotent mutations or by the server for authoritative resources.
- Timestamps are UTC ISO 8601 strings.
- Authentication uses a secure server session. Clients do not submit actor or owner IDs.
- Mutations require `Content-Type: application/json` unless uploading directly to object storage.
- List endpoints use opaque cursor pagination, never offset pagination.
- Unknown request properties are rejected for mutation endpoints.
- Responses include `X-Request-Id`.
- `Cache-Control` is explicit on every public read response.

## Standard error

All non-conflict errors follow `ApiError`:

```json
{
  "error": {
    "code": "VALIDATION_FAILED",
    "message": "The stroke contains an invalid pixel index.",
    "requestId": "req_01J...",
    "details": {
      "path": "chunks[0].changes[4].pixelIndex"
    }
  }
}
```

Supported codes:

- `BAD_REQUEST`
- `UNAUTHENTICATED`
- `FORBIDDEN`
- `NOT_FOUND`
- `CONFLICT`
- `RATE_LIMITED`
- `PAYLOAD_TOO_LARGE`
- `UNSUPPORTED_MEDIA`
- `VALIDATION_FAILED`
- `INTERNAL_ERROR`

`429` responses include `Retry-After`. Validation details never expose stack traces, SQL, storage keys, authentication subjects, or other private fields.

Authenticated mutations store a canonical request hash with their operation UUID. Repeating an operation with the same body returns the stored result; reusing its UUID with a different body returns `409 CONFLICT`.

## Public world endpoints

### `GET /worlds/{worldSlug}`

Returns public world metadata and supported limits.

Response: `200 World`

### `GET /worlds/{worldId}/regions`

Query parameters: `minX`, `minY`, `maxX`, `maxY`.

Returns every region intersecting the requested bounds in descending priority. The client applies the first matching policy at a location.

Response: `200 Region[]`

### `GET /worlds/{worldId}/chunks`

Query parameters: `minChunkX`, `minChunkY`, `maxChunkX`, `maxChunkY`.

Rules:

- Bounds are inclusive.
- A request may cover at most 169 chunks.
- Missing chunks are omitted and interpreted as transparent version-0 chunks.
- Layer payloads use `deflate-base64-rgba`.

Response:

```json
{
  "chunks": [
    {
      "worldId": "00000000-0000-4000-8000-000000000001",
      "chunkX": 0,
      "chunkY": 0,
      "version": 7,
      "encoding": "deflate-base64-rgba",
      "layers": ["...", "...", "..."],
      "updatedAt": "2026-09-08T00:00:00.000Z",
      "updatedBy": null
    }
  ]
}
```

Response: `200`  
Caching: private revalidation using chunk-version ETags; the world response itself is never assumed immutable.

## Pixel operations

### `POST /worlds/{worldId}/pixel-operations`

Authentication: member or higher with active publishing permission.

Request: `ApplyPixelOperationRequest`

```json
{
  "operationId": "eac22290-58fa-4d9f-9db6-970bed21a411",
  "kind": "draw",
  "chunks": [
    {
      "chunkX": 0,
      "chunkY": 0,
      "expectedVersion": 7,
      "changes": [
        {
          "pixelIndex": 129,
          "layer": 1,
          "rgba": [0, 230, 184, 255]
        }
      ]
    }
  ]
}
```

The server validates:

- UUID and idempotency
- Actor status and rate limits
- Coordinate range
- Region policy for every affected pixel
- Layer values
- Unique pixel indices inside an operation
- RGBA channels
- At most 10,000 total affected pixels
- Every expected chunk version

The operation is atomic across all chunks. Either all versions and pixel changes commit or none commit.

Successful response: `201 ApplyPixelOperationResponse`

```json
{
  "operationId": "eac22290-58fa-4d9f-9db6-970bed21a411",
  "worldId": "00000000-0000-4000-8000-000000000001",
  "actorId": "9fd3d66f-e3e9-4be8-a9eb-1d8b7a56f61e",
  "acceptedAt": "2026-09-08T00:00:00.000Z",
  "affectedPixelCount": 1,
  "chunks": [
    {
      "chunkX": 0,
      "chunkY": 0,
      "previousVersion": 7,
      "version": 8
    }
  ]
}
```

Replaying an already accepted `operationId` with an identical body returns the original success response with `200`. Reusing it with a different body returns `409 CONFLICT`.

Version conflict response: `409 PixelOperationConflict`

```json
{
  "error": {
    "code": "CONFLICT",
    "message": "One or more chunks changed before this operation was accepted.",
    "requestId": "req_01J...",
    "operationId": "eac22290-58fa-4d9f-9db6-970bed21a411",
    "conflicts": [
      {
        "chunkX": 0,
        "chunkY": 0,
        "expectedVersion": 7,
        "currentVersion": 8
      }
    ]
  }
}
```

After a conflict, the client fetches fresh chunks. It may automatically retry only when it proves that the intended pixels did not change; otherwise it shows `Retry required`.

For `kind: "undo"`, `undoOfOperationId` is required. The server accepts it only when the inverse patch does not replace a later conflicting edit.

## Entity endpoints

### `GET /worlds/{worldId}/entities`

Query parameters: `minX`, `minY`, `maxX`, `maxY`, optional `cursor`, optional `limit` up to 200.

Response: `200 CursorPage<Entity>`.

Only visible, non-deleted entities are returned. Public creator data contains ID, display name, and public avatar only.

### `GET /entities/{entityId}`

Response: `200 Entity` or `404 NOT_FOUND`.

### `POST /worlds/{worldId}/entities`

Authentication: member or higher.  
Request: `CreateEntityRequest`.  
Response: `201 Entity`.

`operationId` provides idempotency. The server supplies `id`, `creator`, and timestamps. The asset must be ready and usable by the current member.

### `PATCH /entities/{entityId}`

Authentication: owner, except dedicated moderator actions.  
Request: `UpdateEntityRequest`.  
Response: `200 Entity`.

`expectedUpdatedAt` prevents lost metadata or position updates. A mismatch returns `409 CONFLICT` with the current timestamp.

### `DELETE /entities/{entityId}`

Authentication: owner.  
Header: `Idempotency-Key: <UUID>`.  
Response: `200 EntityTombstone`.

Deletion is soft for 30 days. Moderator removal uses the moderation endpoint instead of impersonating the owner.

## Asset endpoints

### `POST /assets/uploads`

Authentication: member or higher.  
Request: `CreateAssetUploadRequest`.  
Response: `201 CreateAssetUploadResponse`.

The response grants a short-lived upload URL for one object. It is not a public asset URL.

### `POST /assets/{assetId}/complete`

Authentication: asset owner.  
Request: `{ "operationId": "<UUID>" }`.  
Response: `202 Asset` with status `processing`.

Completion queues server-side verification and processing. It does not trust upload headers.

### `GET /assets/{assetId}`

Authentication: owner while pending or rejected; public when ready and referenced by visible content.  
Response: `200 Asset`.

Storage keys and private original URLs are never returned.

## Account endpoint

### `GET /me`

Authentication required. Returns private session identity, role, publishing status, usage counters, and configured limits. Public user endpoints use the smaller `PublicUser` representation.

## Report endpoints

### `POST /reports`

Authentication: optional, with stricter anonymous throttling.  
Request: `CreateReportRequest`.  
Response: `201 Report`.

The server consolidates duplicate reports from the same actor or anonymous rate-limit identity.

## Moderation endpoints

### `GET /moderation/reports`

Authentication: moderator or administrator.  
Query: `status`, `cursor`, `limit`.  
Response: `200 CursorPage<Report>`.

### `POST /moderation/actions`

Authentication: moderator or administrator.  
Request: `CreateModerationActionRequest`.  
Response: `201 AuditEvent`.

Actions are atomic with the affected content or account update. Reasons are mandatory. Audit events are immutable.

## Health endpoints

### `GET /health/live`

Reports that the server process is responsive. It does not query dependencies.

### `GET /health/ready`

Reports whether the API can serve traffic. It checks database connectivity and required schema version without exposing credentials or topology.

## Versioning

- Breaking transport changes require `/api/v2`.
- Additive response fields may appear in v1; clients ignore unknown response properties.
- Mutation requests reject unknown properties to detect client mistakes.
- Chunk layer encoding has its own explicit name so compression can evolve without changing the API version.
